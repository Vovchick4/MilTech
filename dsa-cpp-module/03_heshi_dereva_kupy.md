# 3. Хеш-таблиці, дерева, купи

## 3.1 Хеш-таблиця

Ідея: перетворити ключ на індекс масиву функцією `hash(key) % capacity`.

```
"WPNAV_SPEED" --hash--> 0x8F3A...  & 7 = 2      slots: [ . | . | WPNAV_SPEED=1500 | . | ... ]
```

**Колізії** (два ключі в один слот) — неминучі. Два підходи:

| | Ланцюжки (chaining) | Відкрита адресація (open addressing) |
|---|---|---|
| Як | у слоті — список ключів | шукаємо наступний вільний слот (linear probing) |
| Хто | `std::unordered_map` | наша `dsa::HashMap`, `absl::flat_hash_map` |
| Кеш | гірше (вузли) | краще (все в одному масиві) |
| Видалення | просто | потрібні «надгробки» (tombstone) |

**Load factor** = кількість ключів / кількість слотів. При > 0.7 пробінг різко довшає →
таблиця подвоюється (rehash, O(n) разово). Код: `include/dsa/hash_map.hpp`.

> Чому при видаленні не можна просто позначити слот `Empty`? Бо пошук іншого ключа, який колись
> «проскочив» цей слот, зупиниться на ньому і скаже «не знайдено». Тест
> `HashMap: insert/find/erase/rehash` перевіряє саме це (`P778` після видалення `P777`).

**Найгірший випадок — O(n):** якщо зловмисник підбере ключі з однаковим хешем (hash flooding),
таблиця деградує в список. Для real-time — аргумент на користь відсортованого масиву (гарантований O(log n)).

Приклад `./build/04_params_lookup` — пошук параметра за іменем серед 1000:

```
linear search  O(n)     :    93.79 ms
binary search  O(log n) :    23.80 ms
hash map       O(1)     :     4.70 ms
```

## 3.2 Бінарне дерево пошуку (BST)

```
        50
       /  \
     30    70          ліворуч — менші, праворуч — більші
    /  \   / \         обхід in-order: 20 30 40 50 60 70 80 — відсортовано!
   20  40 60  80
```

- `find/insert` — O(h), h = висота.
- Випадкові ключі: h ≈ 2·log n. **Відсортовані ключі: дерево вироджується в «палицю», h = n.**
  Тест `BST: ... degenerate height` вставляє 0..999 і отримує висоту 1000.
- Рішення — збалансовані дерева (AVL, червоно-чорне). `std::map` / `std::set` — червоно-чорне,
  h ≤ 2·log₂(n+1) гарантовано.

Коли `std::map`, а не `unordered_map`: потрібен **порядок** — «перший waypoint після часу t»
(`lower_bound`), обхід за зростанням, діапазонні запити.

## 3.3 Купа (binary heap) і пріоритетна черга

Повне бінарне дерево в масиві, де батько ≤ дітей (min-heap):

```
індекси:        0              масив: [1, 3, 2, 7, 4, 5]
              /   \            батько(i) = (i-1)/2
             1     2           діти(i)   = 2i+1, 2i+2
            / \   /
           3   4 5
```

| Операція | Складність | Як |
|---|---|---|
| `top()` | O(1) | корінь |
| `push()` | O(log n) | в кінець + «спливання» вгору (sift up) |
| `pop()` | O(log n) | останній на місце кореня + «занурення» (sift down) |
| побудова з n елементів | O(n) | `std::make_heap` |

Код: `include/dsa/binary_heap.hpp`. STL: `std::priority_queue` (за замовчуванням **max**-heap;
для min — `std::priority_queue<T, std::vector<T>, std::greater<T>>`).

Де купа на дроні:
- **планувальник задач** — «яка задача наступна за часом» (`./build/03_scheduler_heap`);
- **Dijkstra / A*** — «яка вершина найдешевша» (розділ 5);
- **k найближчих** — купа розміру k (задача T02).

```
Запусків за 1 с:
  read_imu         400 Hz ->  400
  update_gps        50 Hz ->   50
  check_failsafe     1 Hz ->    1
```

> Справжній `AP_Scheduler` в ArduPilot простіший: статична таблиця задач, перевіряється по колу
> кожен тік. Для ~50 задач лінійний прохід по масиву швидший і передбачуваніший за купу — знову кеш і константи.
