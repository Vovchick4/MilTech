# 1. Складність, пам'ять і кеш

## 1.1 Навіщо це на дроні

Контролер польоту ArduPilot крутить основний цикл **400 разів на секунду** — 2.5 мс на все:
прочитати IMU, порахувати регулятори, оновити EKF, записати лог, відповісти GCS.
Якщо одна функція раптом займе 5 мс — регулятори пропустять цикл, дрон смикнеться.
Тому в embedded/real-time важливі не тільки «середній» час, а:

- **найгірший випадок** (worst case), а не середній;
- **передбачуваність**: жодних виділень пам'яті (`new`, `push_back` з реалокацією) у циклі польоту;
- **пам'ять**: на STM32H7 — 1 МБ RAM на все.

## 1.2 Big-O — як росте час зі зростанням n

| Клас | Назва | n = 1 000 | n = 1 000 000 | Приклад |
|---|---|---|---|---|
| O(1) | константа | 1 | 1 | доступ `v[i]`, `push` у кільцевий буфер |
| O(log n) | логарифм | 10 | 20 | бінарний пошук, `std::map::find`, купа |
| O(n) | лінійна | 1 000 | 10⁶ | обхід масиву, лінійний пошук |
| O(n log n) | | 10⁴ | 2·10⁷ | `std::sort`, merge sort |
| O(n²) | квадратична | 10⁶ | 10¹² (!) | insertion sort, «кожен з кожним» |
| O(2ⁿ), O(n!) | експонента | — | — | точний розв'язок задачі комівояжера |

Правило великого пальця: сучасний CPU — ~10⁸–10⁹ простих операцій за секунду.
10¹² — це хвилини або години. Мікроконтролер — у 10–100 разів повільніше.

### Що «ховає» Big-O

- **Константи.** O(n) з константою 100 буває повільніше за O(n log n) з константою 1 на малих n.
  Тому `std::sort` на шматках < 16 елементів перемикається на insertion sort.
- **Кеш процесора** (див. 1.4).
- **Амортизацію** (див. 1.3).

## 1.3 Амортизована складність

`std::vector::push_back` — **амортизовано O(1)**: коли `capacity` закінчується, вектор
виділяє вдвічі більший блок і копіює все — це O(n), але трапляється так рідко, що в середньому на
одну вставку — O(1).

На дроні це пастка: «рідко» = раптова пауза в циклі польоту. Рішення:

```cpp
std::vector<Waypoint> wps;
wps.reserve(MAX_WAYPOINTS);   // виділити ОДИН раз на старті
```

або структура фіксованого розміру — `std::array`, наш `dsa::RingBuffer<T, N>`.

## 1.4 Пам'ять: стек, купа, кеш

| | Стек (stack) | Купа (heap) |
|---|---|---|
| Що там | локальні змінні, `std::array` | `new`, `std::vector`, `std::list`, `std::map` |
| Швидкість виділення | миттєво (зсув вказівника) | повільно (алокатор, можлива фрагментація) |
| Розмір | малий (8 МБ на ПК, кілька КБ на MCU!) | велика |
| Ризик | переповнення від глибокої рекурсії | фрагментація, витоки |

**Кеш.** Процесор читає пам'ять рядками по 64 байти. Сусідні елементи `std::vector` потрапляють у
кеш разом — обхід майже безкоштовний. Вузли `std::list` розкидані по купі — кожен крок = промах кешу
(~100 нс). Запусти:

```bash
./build/01_bench_containers
```

Результат з нашого запуску:

```
vector:    0.38 ms
list  :    4.74 ms   <- той самий O(n), у 12 разів повільніше
vector insert(mid):               2.75 ms    <- O(n) на вставку, але memmove дуже швидкий
list   advance(mid)+insert:     125.39 ms    <- O(1) вставка, але O(n) щоб дійти до місця
std::map           (O(log n)):  410.78 ms
std::unordered_map (O(1)):       26.86 ms
```

> **Висновок:** у 9 з 10 випадків починай зі `std::vector`. Інша структура — тільки якщо є
> конкретна причина і вимірювання.

### Рекурсія і стек

Рекурсивний обхід дерева глибиною 10⁶ = 10⁶ кадрів стека → `Segmentation fault`.
У нашому коді це обійдено явно — подивись деструктори `LinkedList` і `BST`
(`include/dsa/linked_list.hpp`, `bst.hpp`): за замовчуванням `unique_ptr` видаляв би вузли рекурсивно.

## 1.5 Шпаргалка STL

| Контейнер | Доступ [i] | Пошук | Вставка/видалення | Пам'ять | Коли |
|---|---|---|---|---|---|
| `std::array<T,N>` | O(1) | O(n) | — (розмір фіксований) | стек, 0 накладних | розмір відомий на етапі компіляції |
| `std::vector<T>` | O(1) | O(n) / O(log n) якщо відсорт. | кінець — O(1)*, середина — O(n) | неперервна | **за замовчуванням** |
| `std::deque<T>` | O(1) | O(n) | обидва кінці — O(1) | блоками | черга з двох кінців |
| `std::list<T>` | — | O(n) | O(1) за ітератором | вузол + 2 вказівники | splice, стабільні ітератори (LRU) |
| `std::map<K,V>` | — | O(log n) | O(log n) | вузол + 3 вказівники | потрібен **порядок** ключів, діапазони |
| `std::unordered_map<K,V>` | — | O(1)* | O(1)* | кошики + вузли | швидкий пошук за ключем |
| `std::priority_queue<T>` | top O(1) | — | O(log n) | vector | «наступний найважливіший» |
| `std::stack`, `std::queue` | — | — | O(1) | адаптери над deque | LIFO / FIFO |

\* амортизовано / в середньому.

Корисні алгоритми з `<algorithm>`:

| Функція | Складність | Що робить |
|---|---|---|
| `std::sort` | O(n log n) | нестабільне сортування |
| `std::stable_sort` | O(n log n) | зберігає порядок рівних |
| `std::nth_element` | O(n) в середньому | k-й елемент на своє місце (медіана!) |
| `std::partial_sort` | O(n log k) | перші k відсортованих |
| `std::lower_bound` / `upper_bound` | O(log n) | бінарний пошук у відсортованому |
| `std::unique` + `erase` | O(n) | прибрати сусідні дублікати |

## 1.6 Інструменти

- **`-O2` / Release.** Бенчмарки в Debug безглузді — `scripts/build.sh` збирає Release.
- **AddressSanitizer + UBSan:** `./scripts/build.sh asan` — ловить вихід за межі масиву,
  use-after-free, переповнення знакових чисел. Запускай тести задач під ним хоча б раз.
- **Профілювання:** `perf record ./build/06_sort_bench && perf report` (Linux).

## Питання для самоперевірки

1. Чому `push_back` — «амортизовано» O(1), і чим це небезпечно в циклі 400 Гц?
2. Обидва обходи — O(n). Чому `std::list` у 10+ разів повільніший за `std::vector`?
3. Коли `std::map` кращий за `std::unordered_map`?
4. Що станеться з рекурсивною функцією глибиною 10⁶ на мікроконтролері з 8 КБ стека?
